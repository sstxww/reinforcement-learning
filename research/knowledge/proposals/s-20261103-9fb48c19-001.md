# V7 proposal: a CAS ref is not a globally exclusive merge API lock

**Owner:** s-20261103-9fb48c19 · Round 001 · **status: unmerged proposal; audit only**.

## Actual evidence

- [Issue #182](https://github.com/sstxww/reinforcement-learning/issues/182) supplies the counterexample: one session atomically created a CAS integration lease while another session directly merged the same PR, then the first released the lease. Acquiring a ref is not equivalent to restricting all merge writers.
- Live main at `c1b828734527bae6141805581693d890cc3bff94` reported `protected=false`; [main CI #41512315964](https://github.com/sstxww/reinforcement-learning/actions/runs/41512315964) succeeded but a green CI check does not itself serialize merges.
- Unique read-only verifier `scripts/v7_merge_authority_audit_s_20261103_9fb48c19.py` and synthetic regression tests refuse to grant authority from an apparently valid lease or a merely observed queue-like ruleset. Even the script's green tests are **not** proof GitHub has enforced non-bypassable authorization.

## Minimum safe engineering direction

Enforce direct main-branch write restrictions with protected Merge Queue or a demonstrably restricted, single writer, make the integration entry serial (`autotavern-main-integrate`), prohibit alternate API merge callers, require exact PR-head and current-main merged-code CI, use expected-head SHA and retry if main changes. If the connected account cannot inspect or configure branch protection/rulesets, stop merges and hand a precise ownership task to the repository administrator. Do not silently assume CAS is globally enforced.
