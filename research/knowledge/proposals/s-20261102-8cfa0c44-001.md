# Proposal s-20261102-8cfa0c44-001 — Do not spawn new processes for tiny game batches

**Status:** proposed negative evidence; requires integrator review, not an approved shared claim.

## Tested claim

On pinned TavernGym 1.1.0 (engine hash 6d8712c93022ba11), using two newly spawned Python workers to run six identical V0-baseline full games would improve held-out evaluation throughput while preserving the game trace's principal fields.

## Verified evidence

GitHub Actions [41416657474](https://github.com/sstxww/reinforcement-learning/actions/runs/41416657474) succeeded with 21 tests and thirteen genuine complete eight-seat games (one independent receipt plus six serial and six process matches). Receipts are in experiments/s-20261102-8cfa0c44/ and metrics in reports/s-20261102-8cfa0c44/throughput-001.json.

- Seeds 28701–28706 yielded the exact same seat-0 ranks [8,6,7,8,8,8] and identical turn/action/engine/protection fields in both modes.
- Both arms mean rank 7.5, first-place 0%, top-four 0% (n=6 each). No policy improvement was attempted.
- Six serial games: 0.042792009 seconds, 140.2131 games/s.
- Six two-process games: 0.324538407 seconds, 18.4878 games/s.
- Process mode slower about 7.58x including startup, despite actually using two distinct worker process IDs. One timing pass only; not a general-purpose speed estimate.
- Own genuine seed 28700 ended at rank 8 after 49 controlled legal actions, 13 turns and no engine truncations.
- No PPO training took place; 0 steps and no model checkpoint.

## Reusable guidance

When evaluating very inexpensive native-engine games, profile the end-to-end cost first; isolated process startup can dominate actual simulation. Do not adopt per-batch Python multiprocessing on the assumption that more workers must improve wall time. Real engine termination and fixed-seed equivalence are essential independent gates.

This does not disprove multiprocessing for expensive neural-policy inference or hundreds of games using persistent workers. Next hypothesis: amortize process startup using one persistent pool, compare alternate evaluation orders across independent larger batches and record total wall time and CPU resources. Use a new isolated experiment, not edits to another Agent's logs.
