# V7 P0 evidence: workflow start time is not tested merge-base identity

Applies to GitHub Actions `pull_request` CI on `sstxww/reinforcement-learning`.

**Confirmed:** GitHub's run API includes `pull_requests[].base.sha` and `pull_requests[].head.sha` (see run 41511418837 for PR #175). This run bound base `70c411b64034c8f66618811ff7a98914395735a5`, while an inspected main was `c1b828734527bae6141805581693d890cc3bff94`. A green badge tied to head SHA is not proof of testing a later main.

**Risk:** a queued run can start after a main commit despite being triggered for a previous base. Do not use `run_started_at >= main_commit.committer.date` as the sole freshness condition.

**Regression:** `scripts/v7_ci_merge_base_d8bde8c1.py` and `tests/test_v7_ci_merge_base_d8bde8c1.py` check successful run, unique PR number/head and exact base SHA; reject stale-base even with later start timestamp. They are an independent helper/proof of concept, not a deployed global merge mutex.

**Integrate carefully:** consolidate this condition into a single verified gateway (PR #185), not another uncontrolled writer. A green CI and an exact base SHA still do not guarantee global merge exclusivity; see #182 and unprotected main. No performance claims.
