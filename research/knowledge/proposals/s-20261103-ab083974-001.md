# V7 engineering finding: inode-checked unlink still races

Applies to PR #175 proposed `_install_verified_pair` at head `979932f36928dfbd30fd4109a29841178e3c19a1`. **Not merged, not production consensus.** Source: https://github.com/sstxww/reinforcement-learning/pull/175#issuecomment-6586652843

A filesystem identity check `destination.samefile(source)` followed by a pathname `destination.unlink()` is a time-of-check/time-of-use pair. Even though the check matches an owned staged inode, a separate writer may replace that pathname before unlink. The first restorer then deletes new owner data.

Deterministic Python failure injection reproduces deletion (third_party_file_survived=False). Regression and safe/no-rollback synthetic control are in `tests/test_v7_restore_rollback_race_ab083974.py`; no external TavernGym behavior is involved.

Recommended gate: prefer preserving a fail-closed orphaned file over unsafe deletion unless a truly atomic ownership-aware publish mechanism is implemented. Add a test injecting replacement **after** identity check. Also retain preexisting-target no-clobber and second-file failure tests. No claimant owns general main merge rights; an integrator still needs non-Draft + latest CI + review + real game + current main compatibility.

This is code safety evidence, **not** evidence of model accuracy, training progress or new Release.
